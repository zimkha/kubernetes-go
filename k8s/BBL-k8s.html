Définition

Le Rolling Update est une stratégie de déploiement qui remplace progressivement les anciennes instances d'une application par de nouvelles versions, sans interruption de service.

Avantages

  • • Zero downtime
  • • Rollback facile
  • • Consommation ressources modérée
  • • Natif dans Kubernetes

Limitations

  • • Deux versions coexistent temporairement
  • • Plus lent que Recreate
  • • Nécessite readiness probes
  • • Complexe pour apps stateful

Les 5 Phases d'un Rolling Update

1

Création du nouveau ReplicaSet

K8s crée un nouveau ReplicaSet avec l'image v2, mais avec 0 replicas initialement

2

Scale Up progressif (nouveau)

Le nouveau ReplicaSet augmente selon maxSurge. Ex: si maxSurge=1, on crée 1 pod v2

3

Attente Readiness Probe

K8s attend que le nouveau pod soit "Ready" avant de continuer. C'est CRITIQUE !

4

Scale Down (ancien)

Dès que v2 est ready, K8s termine 1 pod v1 (selon maxUnavailable)

5

Répétition jusqu'à complétion

Les phases 2-4 se répètent jusqu'à ce que tous les pods soient en v2

Comment K8s Gère l'Historique

Kubernetes conserve les anciens ReplicaSets (par défaut 10). Chaque déploiement crée un nouveau ReplicaSet mais garde les anciens avec 0 replicas.

Commandes de Rollout

# Voir l'historique des déploiements
kubectl rollout history deployment/mon-app
# Observer le rolling update en temps réel
kubectl rollout status deployment/mon-app
# Rollback vers la version précédente
kubectl rollout undo deployment/mon-app
# Rollback vers une révision spécifique
kubectl rollout undo deployment/mon-app --to-revision=3
# Mettre en pause un rolling update
kubectl rollout pause deployment/mon-app
# Reprendre un rolling update
kubectl rollout resume deployment/mon-app

💡 Astuce Pro: Le rollback est quasi-instantané car il ne fait que réutiliser l'ancien ReplicaSet déjà existant !
